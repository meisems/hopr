# Hopr – Hop Across Chains

A cross-chain trading terminal: a web dashboard where users trade from their own EVM, Solana and NEAR wallets, and a **Telegram bot + Mini App** that trade with an encrypted Hopr wallet after the user confirms a fresh quote. Any token on any of the 7 chains can be bought with any chain's coin — e.g. 1 SOL of a Base token, 1 ETH of a Solana token, or 1 NEAR of either.

## 🚀 Deployment (Cloudflare Pages + Workers)

### Prerequisites
- Node.js 18+
- Cloudflare account with Pages & Workers enabled
- Wrangler CLI: `npm install -g wrangler`

### Frontend (Cloudflare Pages)
```bash
# Install dependencies
npm install

# Build
npm run build

# Deploy to Pages
npx wrangler pages deploy dist --project-name=hopr
```

### Backend (Cloudflare Workers)
```bash
# Deploy worker
npx wrangler deploy

# Create D1 database
npx wrangler d1 create hopr-db

# Create KV namespace
npx wrangler kv:namespace create CACHE
```

### Environment Variables
Set these in Cloudflare Dashboard → Workers → Settings → Variables:
- `ENCRYPTION_KEY` – AES-256-GCM key for wallet encryption
- `LIFI_API_KEY` – LI.FI API key for cross-chain routing. **Required in production**: the dashboard's quotes go through the worker, so without a key every user shares the worker's anonymous LI.FI quota and trading stops once it runs out
- `LIFI_INTEGRATOR` – optional LI.FI integrator override; defaults to `hopr`
- `TELEGRAM_BOT_TOKEN` – token generated by @BotFather
- `TELEGRAM_WEBHOOK_SECRET` – random secret used to authenticate Telegram webhook requests
- `TELEGRAM_MINI_APP_URL` – public HTTPS URL for the Hopr dashboard, used as the Telegram Mini App entry point
- `VITE_API_URL` (dashboard build) – URL of the deployed worker. Enables the LI.FI key proxy and the referral program
- `VITE_WALLETCONNECT_PROJECT_ID` (dashboard build, optional) – free project id from https://cloud.reown.com; adds WalletConnect (QR on desktop, any mobile wallet). Without it, mobile users connect by opening Hopr inside MetaMask / Coinbase / Trust / OKX / Phantom / Solflare via the deep links in the Connect dialog
- `HOPR_INTENTS_FEE_ACCOUNT` (worker) – Hopr's NEAR account. It receives the 0.5% / 1% fee on NEAR Intents routes and on Ref Finance (NEAR ↔ NEAR) swaps; the dashboard reads it from `GET /api/config`. Without it, NEAR routes charge no Hopr fee and earn no referral rewards. The account must exist on NEAR mainnet. `VITE_HOPR_INTENTS_FEE_ACCOUNT` is only a fallback for dashboards deployed without the worker
- `ONECLICK_JWT` (worker secret, recommended) – NEAR Intents 1Click API key. Default authenticated terms split the submitted app fee 50/50. Without a key HOPR keeps the submitted fee and 1Click adds 0.25% on top
- `TELEGRAM_BOT_USERNAME` (worker, optional) – bot username for invite links (`t.me/<bot>?start=ref_<code>`); read from Telegram's getMe when unset
- `PUBLIC_APP_URL` (worker, optional) – dashboard URL for web invite links; defaults to `TELEGRAM_MINI_APP_URL`
- `VITE_RPC_BASE`, `VITE_RPC_ARB`, `VITE_RPC_BSC`, `VITE_RPC_SOL`, `VITE_RPC_NEAR`, … (dashboard build, optional) – keyed RPC endpoints for balance reads; public RPCs are the fallback
- `ADMIN_TOKEN` (worker secret) – bearer token for `GET /api/admin/referral-payouts` and `POST /api/admin/referral-payouts/paid`
- `REFERRAL_MIN_PAYOUT_USD` (worker, optional) – minimum claim, default 5
- `VITE_TELEGRAM_BOT_URL` (dashboard build, optional) – public bot link such as `https://t.me/YourBot`; the dashboard's Telegram links are hidden when it is unset
- `ENVIRONMENT` – `production` or `staging`
- `NEAR_RPC_URL` (secret, recommended) – keyed NEAR mainnet RPC endpoint. Free public NEAR RPCs are heavily rate limited (and `rpc.mainnet.near.org` is deprecated); they are used only as fallbacks after this URL

After deploying the Worker, set its two Telegram secrets and register its webhook, slash-command suggestions, and command menu:

```bash
# Enter the token without echoing it or storing it in shell history.
read -rsp 'Telegram bot token: ' TELEGRAM_BOT_TOKEN; echo; export TELEGRAM_BOT_TOKEN
# Generate a secret and store both values as Cloudflare Worker secrets.
export TELEGRAM_WEBHOOK_SECRET="$(openssl rand -hex 32)"
printf '%s' "$TELEGRAM_BOT_TOKEN" | npx wrangler secret put TELEGRAM_BOT_TOKEN
printf '%s' "$TELEGRAM_WEBHOOK_SECRET" | npx wrangler secret put TELEGRAM_WEBHOOK_SECRET

# Use the same secret for the local registration script and Cloudflare Worker.
export TELEGRAM_WEBHOOK_URL='https://your-worker.workers.dev/telegram/webhook'
export TELEGRAM_MINI_APP_URL='https://your-dashboard.example.com/'
npm run telegram:configure
```

The setup script calls Telegram's Bot API to register the webhook for messages and button callbacks, publish the bot commands, set the bot's profile description and "What can this bot do?" intro, and set the menu button to open the Mini App when `TELEGRAM_MINI_APP_URL` is provided. The dashboard validates Telegram Mini App `initData` server-side and then returns only the public addresses of the user's encrypted custodial wallet. The normal wallet-sync response contains no private keys. It is safe to rerun after deploying. Keep the token and webhook secret out of source control and logs.

For persistent per-chat addresses and preferences, create a Cloudflare KV namespace (for example, `npx wrangler kv namespace create TELEGRAM_STATE`) and bind it to the Worker as `TELEGRAM_STATE` (Workers & Pages → your Worker → Settings → Bindings → Add → KV namespace). If deployments are managed by `wrangler.toml`, also add the returned namespace ID under a `[[kv_namespaces]]` entry with `binding = "TELEGRAM_STATE"`. Linked public wallets are read-only. Custodial wallets and confirmed trading require D1 migrations and ENCRYPTION_KEY. Never send a seed phrase in chat. Without this binding, `/wallet <address>`, `/balances <address>`, and token lookup work immediately, while saved-wallet and preference commands explain that persistence has not been configured.

## 🎯 Features

### Auto Chain Detection
- Paste any contract address → system detects chain automatically
- Base58 → Solana SPL Token detection
- 0x... → Multi-chain EVM probing (DexScreener + RPC fallback)

### Trading status
- Telegram Buy/Sell buttons fetch a fresh LI.FI quote and show a Confirm and submit button.
- Only the explicit confirmation signs and submits the stored, 90-second quote.
- Dashboard Buy requests a fresh LI.FI quote and transaction payload; the connected browser wallet submits only after explicit confirmation.
- A **0.5% platform fee** is included on every LI.FI swap quote using the `hopr` integrator. The fee wallet must be configured in the LI.FI Partner Portal.
- ✏️ **Buy X** takes any amount; with NEAR as the funding chain (/settings), EVM and Solana tokens are bought through NEAR Intents plus a ▶️ Continue step.

### Web trading (non-custodial)
- Connect EVM (any EIP-6963 wallet, or WalletConnect), Solana (Phantom, Solflare, Backpack) and NEAR (Meteor, HERE, Intear, MyNearWallet) wallets from the header
- One-tap buys and % sells on any scanned token, paying from any of the 7 chains: same-chain and cross-chain routes via LI.FI, NEAR ↔ NEAR via Ref Finance, anything involving NEAR via NEAR Intents
- Bridge native coins and USDC between all 7 chains, with live status tracking until delivery
- History, Positions (live PnL) and Analytics are built from the trades you sign — there is no sample data

### Fees
- **0.5% on trades, 1% on bridges**, charged once per trade: LI.FI integrator fee (`hopr`), NEAR Intents app fee, or an `ft_transfer` of 0.5% of the input inside the Ref Finance swap transaction
- Multi-step routes (e.g. NEAR → ETH → a Base token) charge the fee on step 1 only; later steps are fee-free

### Any token, paid with any chain
- EVM ↔ Solana (e.g. 1 SOL → a Base token, 1 ETH → a Solana token): one LI.FI transaction
- NEAR ↔ NEAR: Ref Finance
- NEAR ↔ tokens NEAR Intents lists (native coins, USDC, some majors): one NEAR Intents deposit
- NEAR ↔ any other token: planned as steps through a hub coin — NEAR → ETH on Base (Intents) → token (LI.FI), or token → wNEAR/ETH → … — each step sized from what the previous one actually delivered. On the web the user signs each step; in Telegram, step 2 is one **▶️ Continue** tap (the Mini App continues automatically)

### Referrals
- Referrers earn **25% of HOPR fee revenue after the routing provider share**. Under default authenticated 1Click terms, a 0.5% trade fee splits into 0.25% for 1Click and 0.25% for HOPR. A referred trade pays 0.0625% of volume to the referrer, leaving HOPR 0.1875%. For a 1% bridge, the corresponding amounts are 0.5%, 0.5%, 0.125%, and 0.375%. Without a referral HOPR keeps its entire share
- Links: web `/?ref=<code>`, Telegram `t.me/<bot>?start=ref_<code>`, Mini App `startapp=ref_<code>`. First link wins; no self-referrals
- **Synced across the bot, the Mini App and the web**: a Telegram user is one referral identity (`tg:<id>`) with the same code in `/referral` and the Mini App's Rewards page. Bot and Mini App trades with the Hopr wallet are credited server-side
- Browser wallets accept an invite by signing a free message (EIP-191 / Solana signMessage / NEAR NEP-413), so nobody can bind other people's wallets to their own code
- Every trade is verified before it earns: LI.FI status API (Hopr integrator, sender, integrator-fee split), 1Click status (refund address, deposit transaction, app fee, and saved quote-time agreement), or the NEAR transaction itself for Ref swaps
- Claims above the minimum create USDC payout requests to the owner's wallet (Telegram users: their Hopr EVM wallet); operators list and mark them paid through the admin endpoints
- Requires migrations `0005`, `0006`, and `0007_intents_fee_policy.sql`. Missing LI.FI splits or historical 1Click agreements stay uncredited pending reconciliation. Existing credited balances are not rewritten: reconcile older payouts against provider statements before paying them. Custom 1Click partner terms require updating the accounting policy before use

### Dual Wallet Architecture
- EVM, Solana and NEAR public wallet addresses can be linked to the Telegram bot for read-only balance checks
- Every custodial wallet also has a NEAR implicit account (64-hex id derived from an ed25519 key). Wallets created before NEAR support get one automatically the first time the user opens the bot or the Mini App; the key is AES-256-GCM encrypted like the others
- Telegram trading uses encrypted custodial keys; never send private keys or seed phrases in a group
- Telegram is the wallet-generation and wallet-management entry point; the website dashboard is the platform for browser-wallet trading

### Telegram Bot
- `/start`, `/help` – Welcome and help, with inline navigation buttons
- `/setwallet evm <address>`, `/setwallet solana <address>`, `/setwallet near <account.near>` – Store public addresses for read-only balance checks
- `/swap <amount> <from> <to>` – NEAR swaps via Ref Finance (e.g. `/swap 1 near usdc`); shows a quote with minimum received and one-time storage fees, then signs only after **Confirm swap**
- NEAR token addresses (`token.near` or 64-hex ids) open a market card with Buy 0.5 / 1 / 5 NEAR and Sell 25/50/100% (sized from the live token balance)
- `/importkey near <ed25519:key> [account.near]` – import a NEAR key; named accounts are verified on-chain to hold it as a full-access key, and an existing funded NEAR wallet is never overwritten
- `/wallet` and `/balances` – Read native balances on the supported chains; the Wallet button also offers Link EVM and Link Solana prompts
- `/settings` – Set and view a per-chat funding-chain and slippage preference
- Send a token address – Look up market information from DexScreener
- Telegram's native command suggestions and menu button are configured by `npm run telegram:configure`
- `/api/trade/quote` uses the server-side LI.FI key to prepare a route; the website wallet submits after explicit confirmation
- Telegram trades support native funding, token approvals, signing, and submission after explicit quote confirmation

## 🔒 Security

- Private keys encrypted with AES-256-GCM
- Encryption keys stored in Cloudflare Workers secrets
- Keys decrypted in-memory only during transaction signing
- No keys ever logged or transmitted unencrypted
- CORS headers restrict API access

## 📊 API Endpoints

| Method | Path | Description |
|--------|------|-------------|
| POST | `/api/detect` | Auto-detect token chain |
| GET | `/api/wallet/:address/balances` | Multi-chain balances; for a NEAR account, spendable NEAR plus NEP-141 token balances |
| POST | `/api/trade/buy` | Legacy endpoint; returns 501 (use wallet signing or custodial quote/confirm) |
| POST | `/api/trade/quote` | LI.FI route quote and executable transaction payload; with `chain: "near"` a Ref Finance quote (read-only, or a confirmable custodial quote when Telegram `initData` is sent) |
| POST | `/api/trade/execute` | Confirm a pending custodial quote by `tradeId` (Telegram Mini App `initData` required) |
| POST | `/api/trade/sell` | Legacy endpoint; returns 501 |
| GET | `/api/trade/:id/status` | Legacy endpoint; returns 501 (active routes track provider status) |
| GET | `/health` | Health check |
